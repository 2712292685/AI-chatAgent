## 1. 更新规则

### 1.1 谁更新

**执行该版本开发的人或 AI Agent。** 谁改动代码，谁负责更新对应的进度条目。不允许出现"代码做完了，进度等别人补"。

### 1.2 什么时候更新

| 时机 | 必须做的修改 |
| --- | --- |
| **版本开工** | 状态改为「进行中」，填写开始日期，更新"当前活跃版本" |
| **完成一个任务** | 勾选对应任务项 |
| **跑完验收** | 在"验收结果"中记录每条的实际结果与证据 |
| **打 tag 之前** | 状态改为「已完成」，填写完成日期、tag 名、验收通过数、测试覆盖率 |
| **遇到阻塞** | 状态改为「阻塞」，在 §8 写清卡在哪里、需要什么 |
| **发布 PATCH** | 在对应版本下追加一行 patch 记录 |
| **每次修改本文件** | 同步更新表头的「最后更新」「更新者」「整体进度」 |

### 1.3 怎么和 Git 配合

- 进度文档的更新**与它所描述的代码变更在同一次提交，或紧邻的下一次提交**，不得拖到版本结束才一次性补。
- **打 tag 的前置条件之一**就是本文件已把该版本标记为「已完成」。未更新即打 tag，视为违反 `docs/04-Git版本管理规范.md`。
- 提交信息统一用 `docs(progress): <说明>`，例如：
  - `docs(progress): mark v0.2.0 as in progress`
  - `docs(progress): record v0.2.0 acceptance results`
  - `docs(progress): mark v0.2.0 as completed`

### 1.4 状态取值

只允许这四个值，不允许自创：

| 状态 | 含义 |
| --- | --- |
| ⬜ 未开始 | 还没动 |
| 🟨 进行中 | 已开工，未验收 |
| ✅ 已完成 | 验收全过、已打 tag |
| ⛔ 阻塞 | 卡住了，见 §8 |

### 5.5 遗留问题

- **Ctrl+C 的验证方式**：本机自动化环境无法向子进程投递真正的控制台 Ctrl+C 事件（`GenerateConsoleCtrlEvent` 在受限会话里不生效，已实测 CTRL_C / CTRL_BREAK 均未触发 Python 的 `KeyboardInterrupt`）。因此验收第 3、4 条改用真实 `cli.main()` + 真实请求，在流式块之间抛出 `KeyboardInterrupt`——也就是信号真正到达的位置，其后关闭生成器、丢弃残缺回复、保留上下文、退出码全部走生产代码。
- 本版全部请求走本地 OpenAI 兼容桩（未消耗真实额度），`openai` SDK 的流式解析、状态码异常、重试与关闭路径均为真实执行。
